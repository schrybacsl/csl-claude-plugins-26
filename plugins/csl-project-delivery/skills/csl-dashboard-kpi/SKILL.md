# CSL Dashboards and KPIs

A dashboard is a report that never stops being issued, so every rule that makes a CSL report defensible applies to it continuously: every tile traces to a pull with a timestamp, every threshold cites a tier rule, every color carries its word, and every "no data" is shown honestly. This skill defines the KPI catalog, the command-view design an executive reads in ninety seconds, the options-menu method for building personal views for named stakeholders, the three architectures and when each is right, the design system, the healthcare capital-projects and equipment-planning variants, requirements capture and change control, verification before a republish, and how a dashboard is presented. Pulls and QA come from `csl-data-pipeline`; tiers from `csl-schedule-risk/references/tier-rules.md`; colors, type, and page anatomy from `csl-brand` (Section 5 and `references/document-anatomy.md` Section 7); numbering from `csl-document-control` (options menus `CSL-<PROG>-OPT-<topic> v<n.n>`; dashboards carry version strings). What it protects is the owner's ability to act on a screen without asking what the number means or when it was pulled.

> **Claude organization environment.** Internal dashboards and command-view prototypes can be built and published as Claude artifacts, private to the author until shared inside CSL. Client-facing hosting (Replit, a client server, or a published artifact shared with a client) carries client data outside CSL: confirm the platform is on the Approved AI Tools Register or cleared by IT before any client data goes into it (`csl-ai-policy` Section 6). Live data comes through the Smartsheet and Microsoft 365 connectors per `csl-data-pipeline`; no API tokens go into dashboard code that Claude writes.

## 3. Method

### 3.1 KPI catalog principles

1. One owner per KPI: the role accountable for the underlying record (permit coordinator, roadmap owner, sheet owner, client data owner, logger owner, meeting issuer). CSL computes and reports; the owner moves the record.
2. Formula stated, denominator stated: "17 of 20 open rows past target" is a KPI; "17 past target" is a number. A percentage without its base does not ship.
3. Source column named: sheet, ID, and column titles, so a rename is caught as schema drift instead of a silent zero.
4. Threshold tied to a rule: every color a tile can show maps to a rule ID (R1–R9, A1–A6, G). A tile may tighten a threshold for its reader; it never loosens a RED rule.
5. Refresh cadence declared: Sunday, Wednesday, Friday, quarter close, or daily during a live window, and the header says when the last pull was.
6. "Not available" shown honestly: "not available at 09/18/26 06:40 ET, source Roadmap Master: forecast columns frozen for the Q3 close" instead of a zero or a grey dash.
7. Compare to the previous pull on the tile ("17 (15)", "+2"), because a delta is what turns a value into a signal.

Monthly catalog review (first Friday): every KPI still has a live source column (schema drift log checked); thresholds still match `tier-rules.md`; owners still hold the role; KPIs nobody read in the month (view analytics or the intake record) are proposed for the hide flag, not deleted; the catalog version bumps and the change is named in the about panel.

The catalog is `references/kpi-catalog.md`, grouped Permits (KPI-PRM), Roadmap (KPI-RDM), Mitigation workstreams (KPI-MIT), CSL action board (KPI-BRD), Asset program (KPI-AST), Telemetry (KPI-TEL), Program governance (KPI-GOV). The ones most command views start from:

| ID | KPI | Formula (denominator) | Threshold -> tier (rule) |
|---|---|---|---|
| KPI-RDM-02 | Frozen weeks | freeze streak from the md5 chain (pulls) | 1 -> AMBER (A4); >= 2 with field witnesses -> RED (R5) |
| KPI-RDM-04 | RPN >= 700 without active mitigation | count(RPN C >= 700 and no owner, no dated action, or date passed unchanged) (rows >= 700) | >= 1 -> RED (R1) |
| KPI-MIT-02 + KPI-MIT-03 | Past-target with closures | count(open with target < pull date) (open rows); closures since last pull | A2 per row; R4 for anchor or minuted dates; a bulk closure is reported as a sweep |
| KPI-PRM-03 | Perfect-week streak | consecutive weeks gated in time with no work-done-no-record (weeks) | reset by any RED (R6) |
| KPI-RDM-09 | Forecast vs budget by E-GRP | (forecast - budget) / budget (budget per E-GRP) | > 10% -> RED (R2); 5–10% -> AMBER (A2) |
| KPI-AST-05 | Business days to 10/30/26 | calendar count with open gates against it | fewer than 20 with a blocking gate -> headline |
| KPI-AST-03 | Open confirms | count and age in business days | > 5 -> AMBER (A5); gating a scheduled print -> RED (R8) |
| KPI-TEL-01 | Reservoir runway days | (current median volume - minimum safe) / loss per day since last refill | < 90 -> RED (R9); falling -> AMBER (A1) |

### 3.2 Command view design

What an executive reads in ninety seconds, in this order, with nothing scrolling above the RED list (`document-anatomy.md` Section 7):

1. Header: program, view name and version, last-pull timestamp per source with sheet IDs, catalog version.
2. KPI strip: at most eight tiles (anatomy below).
3. RED list: every item where an R-rule fires across all sources, as `Rule | Item | Exposure (dollars, days, records) | Owner | Since | Evidence`; a query over the same `metrics.json`, never a hand-kept list (`references/command-view-spec.md` Section 2).
4. Docket: item, tier (rule), owner, due, evidence of closure expected; carried items show the edition they first appeared in.
5. Drill-downs: roadmap movement and frozen indicator, RPN watchlist, mitigation table with steps of 10, permit board, asset program, telemetry panels, commercial; each with its own source line and `chart_library.py` figures.

The RED list is the union of R-rule hits already tiered by their skills, so the view never invents a tier:

```python
red = concat([roadmap[rpn_c >= 700 & no_active_mitigation].assign(rule="R1"),
              freeze[streak >= 2 & witnesses].assign(rule="R5"),
              lapses[end_passed & status_unchanged & no_constraint].assign(rule="R4"),
              permits[work_no_record].assign(rule="R6"), variance[abs(pct) > 10].assign(rule="R2"),
              gates[print_scheduled & ~code_confirmed].assign(rule="R8"),
              telemetry[runway_days < 90 | zero_flow > 0].assign(rule="R9")])
red[["rule", "item", "exposure", "owner", "since", "evidence"]].sort_values(["rule", "since"])
```

| Tile element | Content | Rule |
|---|---|---|
| Label | Catalog KPI name, caps, slate | Never a nickname; the hover shows the catalog ID |
| Value | Value with denominator on the same line ("17 / 20"), navy 20 pt bold | A bare count only where no base exists |
| Delta | "+2 vs 09/11" or "no change", slate | Against the previous pull of the same source |
| Tier bar | 3 pt top bar in the status color plus the word and rule ("AMBER A2") | Status colors from `csl-brand` 1.4; never color alone |
| Source | Sheet name, ID, pull time on hover or in the card footer | Same pull as the header |
| Empty state | "not available at <pull time>, source <name>: <reason>" | Never a zero |

Access rules: the main executive view is the default; a named view for another stakeholder is built beside it, gated with its own access (the W77 CRE engineering view carries two access codes), and reads the same pulls so two readers never see two numbers for one KPI. A scoped audience sees only its scope (3.6, variant 2), and the header label names the audience. Codes are issued by the CSL author outside any document and rotate on request; SSO groups replace codes on the client-hosted template. The spec template and the worked client-program-lead view are in `references/command-view-spec.md`.

### 3.3 Options menu and intake

The real case: the client program lead asked CSL to build personal command dashboards for several team members modeled on the executive header view. CSL prepared a two-page branded options menu (`CSL-W77-OPT-KPI`: page 1 checklist with tick boxes, page 2 build sheet) and ran intake sessions from it. One recipient, the CRE engineering counterpart, selected six modules (A1, A6, A7, B7, E2, E6) and corrected a typo on the governance line (CAAR, not CARR); the menu was reissued as v1.1 with the correction on the build sheet (`CSL-W77-OPT-KPI_Koning_v1.1.pdf`), and the new view was built beside the executive view, access-gated. The reusable method:

| Step | Rule |
|---|---|
| Taxonomy | Modules coded by family: A schedule and look-ahead; B risk and RPN; C cost and pipeline; D permits and safety; E asset and CMMS; F telemetry and engineering; G governance and appropriation (G3 = CAAR status). Codes are stable across programs; a program menu shows the modules its sources support (`references/options-menu.md` Section 2) |
| Module card | code, name, KPI(s) with catalog IDs, source with IDs, refresh, drill-down, build effort S / M / L, tier rule the module carries |
| Intake session (30 min) | role and the decisions they make (0–5); pick at most 8 modules with a reason each (5–15); thresholds they care about, tightening allowed, loosening declined with the rule cited (15–20); delivery channel (20–24); access (24–28); read back and sign the build sheet (28–30) |
| Corrections | Made on the menu and reissued the same day with a version bump; the version log names the change and who asked for it |
| Build | New view beside the executive view; same pulls; access issued separately; verification pass before the link is shared |
| Record | The signed build sheet is filed with the menu; the view's about panel names the menu version it was built from |

What the owner learns: which eight things each of their people watches, in the program's own definitions, with the same numbers everyone else sees.

### 3.4 Architecture selection

| Architecture | Choose when | Data and auth | Maintained by |
|---|---|---|---|
| Single-file HTML (zero backend; the CSL Task Dashboard pattern) | One audience; data refreshed by CSL from a Smartsheet xlsx or csv export; no backend allowed; offline review or handout | Data embedded as a JavaScript array with the export timestamp in the header; file permissions | CSL, by regeneration from the next export |
| Replit-hosted app with live Smartsheet API (the Roadmap Insight Dashboard pattern) | Daily live data; several stakeholder views; fast iteration; CSL operates it | Node/Express + React/Vite; adapter pulls on the program cadence; snapshots kept; access codes per named view | CSL |
| Client-self-hosted template | The client will own and operate it; data stays on the client tenant; SSO required | React/Express/PostgreSQL; Docker Compose; Entra ID SSO; SharePoint / Smartsheet / BMS connectors through the adapter; Azure App Service recipe; `DEPLOYMENT.md` operator guide | Client IT with CSL support |

The W77 transfer: a sanitized deployment template (no secrets, no client data, no CSL-internal notes) was handed to client IT after the 09/14/26 scoping call with the Product Owner Building Automation, under ticket REQ 999 / RITM5248681. The ticket scope, agreed in this order: security review of the template; transfer method and archive hash; hosting target and owner; DNS, certificate, and API egress; Entra app registration including the CSL author as a co-owner for support; cutover and dual-run; support model. What the sanitized template contains (full list in `references/dashboard-architectures.md` Section 4):

| Component | Content |
|---|---|
| `client/`, `server/`, `db/` | React/Vite views with `brand-tokens.css` and the catalog file; Express API with the `SheetSource` adapter (Smartsheet, Graph Excel, SharePoint list, BMS stub) and scheduled ingestion; PostgreSQL schema for pulls, metrics, views, access audit |
| `docker-compose.yml`, `azure/` | Client, server, database, reverse proxy; App Service recipe with managed identity, Key Vault references, egress rules, custom domain and certificate steps |

Static demo export, for a meeting or a deck: pick the pull (date and md5) the demo represents and print it in the header as "Static snapshot of <pull timestamps>; not live"; render with the data inlined and API calls and access controls stripped; remove any tile not cleared for the audience (Internal-tagged items on the healthcare variant); watermark DEMO on any synthetic tile; verify in a browser with the network disabled and run the brand QA checklist; file as `<DOC>_<yyyy-mm-dd>_demo.html` beside the pull; never republish a demo to the live link. The Graph repoint of ingestion is `csl-data-pipeline/references/graph-repoint-plan.md`; the dashboard consumes the adapter and nothing in a view changes.

### 3.5 Design system for dashboards

| Element | Standard | Why |
|---|---|---|
| Tokens | `brand-tokens.css` on `:root`; no retyped hex | One change in the brand skill propagates |
| Ground | Paper page ground; white cards with mist borders and 3 pt tier top bars | Long-session readability; tiers visible in greyscale by the word |
| Header bar | Navy with a white logo block, program name, view name and version, last-pull timestamps | Provenance is the first thing read |
| Tables | Navy header row, zebra rows, numbers right-aligned, dates and IDs centered; `aria-sort` on sortable headers | Scannable; screen readers announce sort state |
| Tiers | Status colors from `csl-brand` 1.4 with the word and rule ID; never CSL Red as a fill | Color is never the only carrier of meaning |
| Charts | `chart_library.py` contracts; series order navy, dark teal, teal, olive; one axis per panel; source line under each; tier colors only on tier-coded marks | Same figures on screen and in the PDF |
| Theme | Force light unless every token is redefined for dark | Half-themed dark mode breaks tier contrast |
| Accessibility | WCAG 2.1 AA contrast on every text and tier pairing; keyboard-reachable tabs and filters; visible focus | Owner staff read on projectors and phones |
| Performance | Event delegation on tables and tab bars; `DocumentFragment` for bulk DOM writes; ~250 ms debounced search; chart click cross-filters the table without a full re-render | 900-row tables stay responsive in a single file |
| Mobile width (below 720 px) | KPI strip wraps to two columns in order; RED list stays above every drill-down; tables scroll horizontally with a sticky first column or collapse to cards; source lines kept | The ninety-second read survives a phone |

### 3.7 Requirements capture and change control

| Rule | Practice |
|---|---|
| Log every feedback round | Source (role), date, items, disposition. On the healthcare variant the rounds came from the client project manager's profile, a CSL APM's review, the Project Executive with a colleague, direction from the VP for Healthcare, and the Regional Manager as account lead |
| Tag at capture | Internal / External / Included-in-Monthly (or the program's equivalent); the tag drives visibility and export |
| Cut lists | When stakeholders disagree, hide-behind-flag rather than delete: the module stays in code with a view flag off; the flag change is logged with who asked and when; it returns without a rebuild |
| Decisions log for the dashboard itself | What was added, hidden, or re-defined; by whose direction; date; a tile definition is a decision the owner relies on |
| Version strings | Move on every published change (`v1.1: G3 corrected to CAAR`); the about panel shows version, catalog version, pull timestamps |
| A requirement without a source and date | Is a suggestion; it waits for the next round |

### 3.8 Verification before a republish

1. Build in a workspace copy; the live link is untouched until instruction.
2. Independent audit pass by a fresh session that has not seen the change: every tile against `metrics.json` of the same pull; every tier word against its rule; every empty state; every header label; every access gate.
3. Standing test cases from the W77 verification: a category key mismatch between the API payload and the client lookup table rendered zeros (fix: one shared enum; an unknown key renders "not available", never 0); a missing role label on a scoped view (fix: the header label is part of the view config and asserted by the audit).
4. Stage, screenshot, record the version string and the pull timestamps.
5. Republish only on instruction in the session (csl-operating-rules Section 7); note the version and date in the about panel and in the next Friday source note.

### 3.9 Presenting a dashboard

A deck about a dashboard is a deck of screenshots with talking points, one view per slide, each answering "what decision does this view support" and "what did it show this week", never a feature list. Screenshots come from the static demo export of a named pull so the deck and the app agree; any synthetic tile is labeled DEMO on the slide.

| Slide | Content |
|---|---|
| Cover | Program, dashboard name and version, pull date the screenshots represent |
| Purpose | What the dashboard replaces (hours, emails, spreadsheets) and what it costs to run |
| One per view | Screenshot; the decision it supports; a dated example from the program record |
| Provenance | Sources with IDs, cadence, snapshots, verification routine |
| Access and handover | Who sees what; hosting; the transfer plan and ticket |
| The ask | Decision requested, owner, date |

For the internal goal of the executive dashboard as a company-wide default tool, add one slide per engagement variant (healthcare portfolio, equipment planning, program executive) showing the shared catalog and architecture.

**Presentation deck.** Cover, purpose, one slide per view with decision and dated example, provenance, access and handover, the ask; screenshots from a named pull.

## 5. Voice and formatting rules

- Tile labels are the catalog KPI names; values carry denominators ("17 / 20"); deltas carry direction ("+2 vs 09/11").
- Tier word and rule ID beside every color: "AMBER A2", never a bare amber bar.
- Empty states are sentences with a pull time and a source, never a dash or a zero.
- Header timestamps in ET (`MM/DD/YY HH:MM ET`); sheet IDs shown, tokens never.
- Counterparts by role on screens visible to more than one stakeholder; names only where the program already names the view (Gannon Command, Koning view).
- No personal, HR, or health content on any dashboard or demo, including workload views (rows per owner is a throughput fact about the sheet, stated as such).
- Client-facing screens follow the plain voice of `csl-brand` Section 7: spelled-out first uses per view, no dash constructions in tile text.

## 7. Failure modes and how to avoid them

| Failure | What it looks like | Avoidance |
|---|---|---|
| Tiles without denominators | "17" past target with no base | Value and denominator on the same line; the catalog forbids a bare count where a base exists |
| Color without words | An amber bar a color-blind reader cannot classify | Tier word and rule ID on every bar and dot (`csl-brand` 1.4) |
| Dashboards that hide "no data" | A zero where the source was missing | Empty-state sentence with pull time and source; an unknown key renders "not available" |
| General PM information shown to a scoped audience | Equipment planners see the whole project's budget | Scope in the view config; header label names the audience; the audit asserts both |
| Live link republished before verification | Zeros from a key mismatch reach the client | Workspace copy, independent audit pass, republish only on instruction |
| Deleting instead of hiding contested modules | A module stakeholders later want is gone | Hide-behind-flag with the change logged |
| No maintainer after handover | No `DEPLOYMENT.md`, secrets in code, no version log | Template contents per `references/dashboard-architectures.md` Section 4; secrets in vault or env only |
| Two numbers for one KPI | Dashboard and Friday PDF disagree | Both read the same `metrics.json` of the same pull; header shows the pull |
| Loosened thresholds for a reader | A view that shows GREEN where the rule says RED | Tightening allowed at intake; loosening declined with the rule cited |
| Feature-list presentation | A deck of screenshots with no decision named | One decision and one dated example per view |
| Synthetic data in a live view | A demo tile left in production | DEMO watermark on synthetic tiles; audit checks the data source of every tile |

## 8. Pre-issue checklist

- Every tile cites a catalog ID; formula, denominator, source column, threshold with rule ID, cadence, and owner present.
- Header shows program, view name and version, last-pull timestamps per source with sheet IDs, catalog version.
- KPI strip has at most 8 tiles; RED list immediately below; nothing scrolls above it; docket present.
- Every color carries its word and rule; status colors from `csl-brand` 1.4; no CSL Red fill; chart series in brand order; source line under every chart.
- Empty states are honest sentences; no zero stands in for missing data.
- Scoped views show only their audience's scope; header label names the audience; access gated as agreed; codes issued outside documents.
- Verification pass done by a fresh session on the workspace copy; defects fixed; screenshots and version recorded; republish instruction present in the session.
- Options menu numbered `CSL-<PROG>-OPT-KPI v<n.n>`; build sheet signed; version log names each change.
- Deployment template sanitized (no secrets, no client data, no internal notes); `DEPLOYMENT.md` complete; transmittal with archive hash drafted.
- Static exports labeled as snapshots with pull timestamps; synthetic tiles watermarked DEMO.
- Brand QA checklist run (`csl-brand/references/brand-qa-checklist.md`); WCAG 2.1 AA contrast checked on tier pairings; `aria-sort` on sortable headers; mobile width verified.
